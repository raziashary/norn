Nothing here is implemented; no P06 code, data or measurement has run. Facts below were read from the current source on 13 November 2026 and the start-adversary review of the same day.

## 1. What exists today (verified in source)

- Access: `Access.check(operation, object_id)` (`src/norn/governance/access.py`) grants only on the newest `scope_grants` row with `scope='*'` for the principal and operation, then, for an object, requires the object to exist and have no tombstone. `scope_grants.scope` is stored but only `'*'` is ever written or read. The denial code is the single `NOT_AUTHORIZED_OR_NOT_FOUND`. Retrieval re-checks the epoch (`QUERY_SECURITY_CHANGED`). There is no per-object or per-scope rule and no non-raising predicate.
- Benchmark publication carries `allowed_principals` per source and rejects any public source the querying principal cannot see (`PUBLIC_PERMISSION_LEAK`); the engine does not read it, so the engine has never been asked to hide an object from a principal that holds a namespace-wide grant.
- Graph: the canonical `relationships` table is atom-to-atom with `relation_type` limited to SUPERSEDES, CONTRADICTS and ADDITIONAL_EVIDENCE (a CHECK constraint, which SQLite cannot alter in place); the projection capability CHECK (`003_projection.sql`) allows only `lexical` and `dense`; schema version is 5 (`database.py`).
- Entities: an atom without a governed external key gets its own PROVISIONAL entity keyed on its span and atom id (`registry.py`); shared identity needs `register_entity` with ADMIN (`identity.py`); no benchmark code calls it.
- Data: `partition(seed, tier)` builds one cluster per family E1 to E14; only E4 has more than 10 sources in a namespace; the published query allows 10 candidates and the baseline adapter uses it for both the candidate and the output limit (`baseline.py`).

## 2. Per-object ACL design (owner decision needed before any code, ADR-0029 P06-Q7)

Goal: a principal with a namespace READ grant can still be denied specific objects, and graph traversal, counts, paths and context never reveal a denied object (blueprint invariants I3 and I8; ADR-0029 P06-Q7). Non-goals: network authentication (the host still supplies the identity), per-field redaction, attribute-based policy, and any claim of constant-time denial.

**Recommended design (D1 to D4 are the decisions):**

- **D1 granularity: scope labels on sources.** Every source carries one scope label in a new `object_scopes(ns, object_id, scope)` table (default `'*'`, which keeps every existing record readable exactly as today). Grants reuse `scope_grants` with `scope` set to a label. Derived objects (events, atoms, entities, spans, support rows, graph edges) do not copy a label; their visibility is computed from their sources at read time, so a label change takes effect everywhere at once. Alternative: a grant row per object (finer, but grant count grows with data and every derived object needs its own row).
- **D2 decision rule: deny overrides, newest epoch wins per scope.** A principal may perform an operation on an object with label S iff the newest `scope_grants` row for `(principal, operation, S)` is GRANT, or there is no row at S and the newest row at `'*'` is GRANT. A REVOKE at S therefore overrides a GRANT at `'*'`. Tombstones still deny everything. Alternative: allow-overrides (rejected: a stale broad grant would silently re-open a revoked label).
- **D3 multi-source objects: fail closed.** An atom or event is eligible iff every source that contributes to its value is eligible; its citations are filtered per support so a reader never receives a span from a denied source; a graph edge is eligible iff both endpoints and every support of the edge are eligible. Alternative: eligible if any support is readable (rejected: the value may have been derived from the denied source).
- **D4 time: current ACL at query time with an epoch re-check.** A historical-snapshot read applies today's grants, never restoring access that was revoked since (this is the existing `QUERY_SECURITY_CHANGED` behaviour). Alternative: ACL as of the snapshot epoch (rejected: it would let a revoked principal read old data).

**Mechanics shared by all four options.** A pure, non-raising `eligible(operation, object_id) -> bool` is added; `check()` stays the raising public gate and is rebuilt on it so there is one rule. The eligible subgraph is built before transition normalization and before candidate ranking; a denied node cannot be an intermediary; hop, fan-out, visited-node and path counts, truncation flags and explanation text are computed over the eligible subgraph only. Denied and absent objects keep one indistinguishable outcome. Setting or changing a label needs ADMIN, publishes `ACCESS_CHANGED` and bumps the security epoch. The benchmark maps each distinct published `allowed_principals` set to a label and queries through one `Engine` per principal (the existing peer pattern in `tests/test_corrections.py`).

**Negative controls required (each must fail on the old code):** a denied neighbour leaves the response bytes unchanged (compared with the neighbour absent); a denied bridge node is never traversed and the path that needed it is reported as unavailable, not as a shorter path; counts and truncation flags do not move when a denied object is added; a REVOKE at a label overrides a `'*'` GRANT; a label change mid-read raises `QUERY_SECURITY_CHANGED`; a multi-source atom with one denied source is hidden; citations from a denied source are dropped while a readable support remains. Known limit to disclose: response time can still differ (not claimed constant).

**Cost of the change:** one table in migration 006 (section 3), `access.py` and the retrieval call sites that pass an object id (54 `check` calls exist today; most are namespace-level and unchanged), and a shipped-contract change to the denial semantics. This is why the design goes to the owner first.

**2a. Atom and entity visibility details (owner answers of 13 November 2026, during T16 preparation).** Atoms and events: only the primary support decides visibility (the primary span of `atoms.source_span_id`, the `source_version` of an event); additional supports from a denied source are dropped from citations and the atom stays (owner answer, recommended option). Entities: the owner asked to explore a ranked and weighted rule over all contributing sources first, with "any readable contributing source" as the fallback. Contributing sources of an entity are its provisional span, its alias spans and the atoms that name it as subject or object. Findings of the exploration (decided: the owner chose R2, any readable contributing source, on 13 November 2026):

- *Ranking by role is safe.* A fixed, host-owned order (identity registration or defining span above alias span above atom mention) is deterministic, auditable and independent of data volume.
- *A weighted sum with a threshold is not safe.* Visibility would then depend on how many readable mentions there are, so a popular hub with many public mentions would outweigh one private defining source and expose an entity whose existence was private (frequency granting access, against I3 and AGENTS "frequency never grants access"); the threshold boundary would also reveal denied weight in counts and paths. Weights may rank which readable source supplies a displayed alias or evidence; they may not grant visibility.
- *Defining-source rule has an ordering hazard.* An entity's provisional span is whichever source mentioned it first, so visibility for everyone would depend on ingest order unless the benchmark loader registers each shared entity by governed external key, in which case the registering span is chosen by the host and is stable.
- Candidate rules: (R1) role-ranked, lexicographic: the entity is visible iff its highest-ranked contributing source (the registration or defining span) is readable, lower-ranked sources only filter aliases, citations and edges; (R2) any readable contributing source, CHOSEN: visible iff at least one is readable, aliases and edges from denied sources dropped; (R3) literal fail-closed over every contributing source (rejected by the owner's reading as too conservative for hubs, kept as the strictest bound).
- Negative controls needed for any choice: a denied-only entity is invisible and absent from counts; an entity with one denied and one readable mention behaves exactly as the chosen rule says; adding a denied mention never changes the response bytes for a principal who cannot read it when R2 applies, and R1 is invariant to adding public mentions. Chosen rule R2 needs the first two plus the byte-identity control.

## 3. Migration 006 (additive, no table rebuild)

SQLite cannot alter a CHECK constraint, so the plan avoids touching `relationships` and the projection table. Migration 006 adds: `relation_types` (the allowed typed relations as rows: MENTIONS, PART_OF_EVENT, OBSERVED_IN, OCCURRED_BEFORE, OCCURRED_AFTER, RELATED_TO, REQUIRES, CONTRADICTS, SUPERSEDES, DERIVED_FROM, HYPOTHESIZES_CAUSE, VERIFIED_CAUSE, IDENTITY_LINK, each with a `traversable` and a `causal` flag, HYPOTHESIZES_CAUSE never causal); `graph_edges` (edge id, typed `from_id/from_kind/to_id/to_kind`, relation type, epistemic, status, scope, validity interval, producer revision, commit_seq) plus `graph_edge_support` (edge to source span); `object_scopes` (section 2); and `graph_manifests` (capability fixed to `graph`, security epoch, source snapshot, builder revision) so the capability constraint of the existing projection table stays untouched. Edges are written with their own object id (kind `graph_edge`) so tombstones, erasure and access apply to them. Proofs required (each separate, AGENTS.md): a fresh v6 schema; a populated v5 database upgraded after a verified backup; an interrupted upgrade that recovers; a restore; and an installed-wheel run that applies the migration. `SCHEMA_VERSION` becomes 6.

## 4. Entity identity policy for the benchmark

A shared entity node may arise only from (a) an identical governed external key that appears in the published source text (for example a record or service tag), registered by an ADMIN-level fixture loader through `register_entity`, or (b) an explicit, source-grounded alias statement in the text, stored as an `IDENTITY_LINK` edge with its span as support. Name similarity never merges (blueprint 15.3; ADR-0029 P06-Q2). The fixture generator must therefore put the external key or alias statement into the rendered text for every chain and hub family; the gold identity table stays evaluator-only. Without that, chain and hub tests would exercise nothing (the adversary's finding 3).

## 5. Fixture version `public-v2` (P06-T18, T19)

- Families: M1 two-hop chain, M2 three-to-four-hop chain with an alias, M3 hub (12 to 40 decoy neighbours around one popular entity), M4 private bridge (the only path crosses a denied label), M5 same-name wrong-seed distractor, M6 near-duplicate episodes with one distinguishing field. Scenario and entity families are split before any paraphrase.
- Pools: a namespace holds 20 to 60 sources so pools exceed the 10-candidate cap. The published query keeps `max_candidates=10` as the output limit and gains an explicit `search_budget` (candidate pool for graph and conventional arms alike, default 60); this changes the published schema and digest, so the version tag moves to `public-v2` and R0 to R3 are re-run on it (P06-T20).
- Roles and power (proposal, values to be fixed in the T21 margin proposal): pilot 24 clusters (to estimate the endpoint variance), tune 48, evaluation 200. For a +0.05 benefit at the pilot standard deviation 0.25 the 80 percent power sample is about 196 clusters (R33); the pilot decides whether that figure holds. The P05 evaluation role is not reused.
- Noisy stratum (`NOISY_V1`, T19): a seeded, deterministic renderer applies typos, abbreviation, clause reordering, distractor clauses and the existing en/id/mixed variants to the same facts; it uses no model, no network and no Groq. The template read-back graph stays as the labelled zero-extraction-error control. A generative renderer would need explicit per-run enablement and is not part of M1.

## 6. Seed definitions (P06-T03)

- **Seed vector:** the nonnegative, sum-one weights over eligible canonical anchors, built after ACL, time and erasure filtering from the exact, BM25 and dense (T0) channels, with channel name, model and version recorded.
- **Fixed seeds:** one seed vector per query, computed once and handed identically to every G arm that uses the conventional channels (G1 to G4), so an arm difference cannot come from different seeds.
- **Shared seeds across graphs:** the same seed vector reused over the gold-derived, template-derived and noisy-derived topologies, so a topology difference cannot come from different seeds. G6 uses exact and graph-structural seeds only; G5 uses the T0 dense channel seeds only (ADR-0029 P06-Q6).
- **Label independence:** seed construction imports nothing from the evaluator or gold modules (a static import test) and a test shuffles the gold labels and asserts the seed vectors are byte-identical.
- **Degraded channels:** when the scoped corpus exceeds the candidate limit the exact channel returns nothing today; seed construction must report `EXACT_CHANNEL_DEGRADED` in the seed record instead of silently dropping it.

## 7. Endpoints (preregistered, margins fixed in P06-T21 before any tune-role read)

Primary: slot recall (complete evidence set) on M1 to M4 for G3 minus G0. Reported separately, never combined: sufficiency status correctness, false answer, false abstention. Cost and efficiency: visited nodes and edges, repeated-transition work, wall time, evidence tokens, useful extra evidence per 1,000 visited nodes. Harm: privacy incidents (zero tolerance, any single one fails), false association rate on M3 and M5. Contrasts: G3 minus G0 (primary), G3 minus G1 (does diffusion beat bounded BFS), G2 and G4 minus G3 (secondary), G6 minus G3 (dependence on semantic search), G5 minus G3 (seed channel), oracle versus derived topology (descriptive and labelled unequal). Pilot-derived numeric margins, the evaluation of the E3 mechanism and the cluster counts are proposed to the owner in `p06_margin_proposal.md` after P06-T06 and frozen only by the owner's written answer.

## 8. Compute and budget scale

Local CPU only, no network. Every study writes its wall-time cap into its receipt before it starts and stops to ask on expected overrun; for the R0 to R3 re-run the owner chose (13 November 2026) a cap set from a measured pilot-role per-query time at 1.5 times the projected total, stopping to ask if the projection exceeds 8 hours (R3 repeats take about 6.6 seconds per query, so the R0 to R3 re-run on `public-v2` is estimated at hours, not minutes, and its cap is set from a measured per-query time on the pilot role). Traversal budgets are global across iterations (unique nodes, unique edges, hops, fan-out, repeated-transition work, deadline) and `MAX_EXPANDED_HITS` stays. Budget-scale tests use a synthetic graph of about 5,000 events and 40,000 to 100,000 edges built in memory by the test (blueprint 22.1), not a fixture namespace, so that the caps can actually bind.
